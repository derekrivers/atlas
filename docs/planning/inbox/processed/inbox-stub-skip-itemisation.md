---
title: "Skip itemisation floods the tick output: aggregate routine non-candidates, itemise only exceptional declines"
objective: "A sync tick reports the skips an operator can act on and aggregates the ones they cannot, so the summary stays readable on a full board and a genuine decline is visible rather than buried."
context: "Live finding, 2026-07-17, on the first tick after ATLAS-170 (#205) merged. A no-op sync printed its summary — `pm sync: completed; pushes=0 ... status_unchanged=58 push_skipped=141` — followed by 141 itemised lines, every one of the form `push skipped ATLAS-N: status not pushable (done)` / `(needs_human_decision)` / `(rejected)`. The tick did nothing and said so in 142 lines. This is a spec defect in ATLAS-170's D-2, authored by the reviewer, not an implementation error: the decision said 'selection loops that decline candidates name the reason per declined candidate', and the agent implemented exactly that. The spec conflated two loops with different shapes. In the REPAIR sweep the candidate set is small and targeted, and one silent skip cost the operator 20 minutes of diagnosis — itemising is correct there. In the PUSH loop the 'candidate set' is the entire board, of which ~95% is permanently outside the working set (done, rejected, needs_human_decision). Those are not declined candidates; they were never candidates. The consequence is worse than the silence ATLAS-170 replaced: 141 lines of noise per tick trains the operator to ignore the output, which defeats the ticket's purpose — and the one genuinely diagnostic skip, if it ever occurs, arrives buried in the flood. Note the same flood will recur under a different reason as the board fills: once many tickets sit in pushable states with unchanged definitions, `cursor already stamped` becomes the new 141. Pre-ruled decisions: D-1 `SyncDecision` gains a classification distinguishing ROUTINE skips (expected states of a healthy board) from NOTABLE ones (a ticket that reached the working set and was then declined). D-2 ROUTINE is exactly: `status not pushable (<status>)`, `cursor already stamped`, and repair mode's `header already present`. These are structural filters, not decisions about a candidate. D-3 NOTABLE is everything else — `no external id`, `updated earlier in this tick`, `definition cursor is stale`, `external id not found in project pull`, `context pack render failed` — each itemised one line, as today. These are rare, diagnostic, and are the lines ATLAS-170 existed to surface. D-4 ROUTINE skips are aggregated into the summary by reason with counts and never itemised by default: `push_skipped=141 (not pushable: done=71, needs_human_decision=54, rejected=8, in_progress=3, review_required=2)`. Grouping by the reason string yields this for free — the status is already in the text. D-5 `-v/--verbose` itemises ROUTINE skips too; the information is never lost, only defaulted away. D-6 `--repair-packs` keeps its repair lines exactly as ATLAS-169/170 deliver them; only its `header already present` skips become routine. D-7 no counter's value, no exit code, and no WARNING behaviour changes — this ticket changes what is printed, not what is done or measured."
