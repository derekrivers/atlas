Root cause is structural, not accidental: WORKFLOW.md dispatches Codex with `shell_environment_policy.inherit=core`, which strips the operator's exported `GITHUB_TOKEN`; the session therefore authenticates with whatever on-disk git credential the sandbox can reach, which is a DIFFERENT token from the operator's and may carry different scopes. The operator's own `atlas preflight` cannot detect this — it would probe the operator's token, not the agent's. The check must run inside the agent's session, which means the hook. Pre-ruled decisions: D-1 `hooks.before_run` gains a write-access probe that runs in the agent's own environment, after the existing `git fetch origin main` freshness step (ATLAS-168). Symphony's `before_run` failure aborts the attempt — that is exactly the desired semantic, and it costs seconds. D-2 the probe is read-only and non-mutating: `git push --dry-run` against the current HEAD (or an equivalent that exercises the credential without creating a ref). It must not create branches, tags, or refs on the remote. D-3 the failure message names the cause in the agent's transcript — no write credential for `<repo>`, session env is `inherit=core`, the operator's exported GITHUB_TOKEN is not visible here — so the operator diagnoses in one read instead of an hour. D-4 no token, credential, or secret value appears in WORKFLOW.md, in any committed file, or in the probe's output; WORKFLOW.md is public. Injecting a token via `shell_environment_policy.set` is REJECTED for exactly this reason. D-5 this is a contract change (WORKFLOW.md front matter + symphony-integration.md), delivered as a normal PR against this repository; NO Symphony code changes (the ATLAS-168 D-1 precedent). D-6 the operator-side credential facts (two auth channels: Atlas reads `GITHUB_TOKEN`; agents use on-disk credentials via the gh credential helper) belong in `operator-environment.md`, not the repository — out of scope here, recorded as an operator action."
